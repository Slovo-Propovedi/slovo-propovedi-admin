# Договорённости (conventions)

Этот документ описывает **процессные договорённости людей** — то, что нельзя (или нецелесообразно) проверить машиной. Это **тонкий cross-cutting слой**: здесь живёт то, что применимо к обоим приложениям монорепозитория и к документации. Специфика каждого приложения (стиль кода, команды, тесты) — в [`frontend/conventions.md`](./frontend/conventions.md) и [`backend/conventions.md`](./backend/conventions.md), здесь не дублируется.

**Статус:** актуально

## OpenAPI-first workflow (главное)

Проект работает по **OpenAPI-first**: единая спецификация — **источник истины** для всех API-контрактов, а zod-схемы и клиенты генерируются из неё с обеих сторон. Спецификация **живёт в отдельном внешнем swagger-репозитории** и доступна по URL `https://docs.slovo-propovedi.ru/openAPI.yaml` (версия v0.4.0 «Admin API — Слово.Проповеди»). Этот же URL захардкожен в обоих конфигах кодогенерации.

> ⚠️ Полное описание конвейера (конфиги, выходные каталоги, команды, патчи) — в [`contracts/rest-api.md`](./contracts/rest-api.md). Ниже — только правила процесса.

### Процесс изменения API

1. **Отредактировать спецификацию** в swagger-репозитории (вне этого репозитория) и задеплоить её на `docs.slovo-propovedi.ru`.
2. **Регенерировать обе стороны** (см. ниже), чтобы бэкенд и фронтенд взяли новые контракты.
3. **Закоммитить** все сгенерированные файлы вместе с изменениями кода.

> ✅ Если спецификация меняется, **обязательно** регенерируются И бэкенд, И фронтенд. Пропуск одной стороны — источник «тихой» рассинхронизации контрактов.

### Команды регенерации

| Действие | Команда |
|----------|---------|
| Backend (zod-схемы Orval) | `cd backend && npm run gen:schemas` |
| Backend из корня | `make gen-backend` |
| Frontend (SDK @hey-api) | `cd frontend/web-app && npm run gen:api` |
| Frontend из корня | `make gen-frontend` |
| Обе стороны сразу | `make gen-api` |

### Свежесть сгенерированных схем

Если сгенерированный код «устарел» относительно спецификации — регенерируй. Типичный признак: `git diff` по `backend/src/generated/` или `frontend/web-app/src/lib/api/generated/` пустой, но спецификация изменилась. Для CI можно проверять свежесть:

```bash
cd backend && npm run gen:schemas && git diff --exit-code -- src/generated/ \
  || (echo "Generated schemas are stale. Run: npm run gen:schemas" && exit 1)
```

## Git

- **Ветки:** feature-ветки от `main`. MR должен быть маленьким и самодостаточным.
- **Формат коммита:** conventional commits (`feat`, `fix`, `refactor`, `test`, `docs`, `style`, `chore`). Заголовок — до 100 символов.
- **Pre-commit:** Husky (`package.json` → `prepare: husky`).
- **MR-процесс:** каждый MR сопровождается описанием «что и зачем», ссылками на изменённые модули и на обновлённые документы `docs/`.

## Docker и секреты

| Команда | Назначение |
|---------|------------|
| `make up` | поднять контейнеры (docker compose up -d) |
| `make down` | остановить и удалить контейнеры |
| `make restart` | down + up |
| `make encrypt` | зашифровать `.env` → `.vault` (ansible-vault, интерактивный пароль) |
| `make decrypt` | расшифровать `.vault` → `.env` (ansible-vault) |

> ⚠️ Требуется установленный `ansible-vault`. `.vault` закоммичен, `.env` — в `.gitignore`. Никогда не коммить `.env`.

Команды проверки стиля, тестов и сборки — в [`frontend/conventions.md`](./frontend/conventions.md) и [`backend/conventions.md`](./backend/conventions.md).

## Работа с AI-агентами

- Задача даётся через ссылки на `docs/frontend/`, `docs/backend/`, `docs/contracts/` — а не через ссылки на код. Агент читает нужный документ из `docs/` ПЕРЕД стартом.
- Перед реализацией агент ОБЯЗАН прочитать: `architecture.md` (для архитектурных изменений), документы затронутых модулей/контрактов.
- После изменения кода агент ОБЯЗАН обновить затронутые документы `docs/` **в том же PR/коммите**. Изменение кода без обновления `docs/` — неполное изменение.
- Каждое срезанное решение фиксируется в `docs/debt.md` в том же PR (см. ниже).
- Машино-проверяемые команды агент запускает из DoD-чеклиста (ниже).

## Ведение документации docs/

- **Язык:** русский. Технические термины и кодовые идентификаторы — английским как есть.
- **Структура каждого типа документа** предсказуема и задана в [`README.md`](./README.md) (карта) — новый документ создаётся по тому же шаблону, что и соседние. Каждый документ заканчивается секцией `## Связанные документы`.
- **Перекрёстные ссылки** между документами и на конкретные пути в коде (`backend/src/sermon/sermon.service.ts`, `frontend/web-app/src/lib/`) — обязательны и относительные (`[architecture.md](./architecture.md)`).
- **Не выдумывать факты.** Если факт неизвестен — посмотреть в коде или оставить пометку `<!-- TODO: уточнить -->` и записать в `debt.md`.
- **Решения не стираются:** отменённое решение помечается зачёркиванием с объяснением в `decisions.md` (секция Superseded), а не удаляется.
- **Формат долга** (в `debt.md`): `- [ ] <что> — <где (пути файлов)> — <когда вернуться>`. Закрытое: `- [x] ...`.
- **Разделение по репозиториям:** документация фронтенда — в `docs/frontend/`, бэкенда — в `docs/backend/` (см. [`README.md`](./README.md) → «Разделение репозиториев»). Не клади специфику приложения в корневые `docs/`.

## Definition of Done (DoD)

Чеклист перед завершением PR:

- [ ] backend: lint, тесты — без ошибок (см. [`backend/conventions.md`](./backend/conventions.md));
- [ ] frontend: `svelte-check`, сборка — без ошибок (см. [`frontend/conventions.md`](./frontend/conventions.md));
- [ ] `docs/` обновлены в том же PR (затронутые `frontend/`, `backend/`, `contracts/`, `architecture.md` при необходимости);
- [ ] срезанные углы записаны в `docs/debt.md`;
- [ ] новые зависимости — только через `docs/decisions.md` (Approved stack);
- [ ] коммиты — conventional commits, заголовок ≤ 100 символов;
- [ ] при изменении API — спецификация обновлена во внешнем репозитории, обе стороны регенерированы, сгенерированные файлы закоммичены.

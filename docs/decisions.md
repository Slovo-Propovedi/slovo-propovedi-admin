# Стек и решения (decisions)

Этот документ фиксирует **утверждённый стек** и принятые решения (ADRs). Изменения вносятся только через обсуждение и редактирование этого файла. Агенты НЕ добавляют зависимости вне раздела Approved stack без объяснения «почему» в этом же документе. Каждое решение оформлено по схеме **Контекст / Решение / Последствия**.

> Решения, относящиеся только к backend (валидация `nestjs-zod`, SQL-миграции, защита self-delete), документируются в репозитории `slovo-propovedi-backend` и здесь не дублируются.

## ADR-001: Разделение админки и API в отдельные репозитории

**Контекст.** Раньше admin-панель была монорепозиторием с двумя приложениями (`backend/` NestJS API + `frontend/web-app/` Svelte SPA) и общей Docker-инфраструктурой. API потребляет несколько клиентов платформы (сайт, mobile), и его изменения по ритму и ответственности не совпадали с изменениями админ-интерфейса. Фронтенд развивается независимо и не обязан коммититься/версионироваться вместе с бэкендом.

**Решение.** Админ-фронтенд вынесен в **отдельный git-репозиторий** (`slovo-propovedi-admin`), а backend остался в своём репозитории (`slovo-propovedi-backend`). Контракт между ними — общий OpenAPI (живёт во внешнем swagger-репозитории `slovo-propovedi-docs`), поэтому git-расположение сторон не влияет на их связность.

**Последствия.**

- Этот репозиторий — standalone-фронтенд; вся его документация — в `docs/`.
- Документация backend переехала в `slovo-propovedi-backend` (co-location с кодом); контракт REST API — общий, описывается в [`docs/contracts/rest-api.md`](./contracts/rest-api.md).
- Каждое приложение получило собственный цикл CI, релизов и версионирования.
- Разделение выполнено; инфраструктурные артефакты (в первую очередь `docker-compose.yml`) перенесены в репозиторий backend.

## ADR-002: OpenAPI-first кодогенерация

**Контекст.** У платформы несколько клиентов (сайт, admin, mobile), которые потребляют один REST API. Ручное дублирование типов и клиентов по сторонам неизбежно рассинхронизируется и порождает баги контрактов. Одна спецификация, сгенерированная в разные клиенты, — единая точка истины.

**Решение.** Единая OpenAPI-спецификация «API — Слово.Проповеди» — источник истины (версия — в `info.version` внешнего `openAPI.yaml`). Она живёт во **внешнем swagger-репозитории** (URL `https://docs.slovo-propovedi.ru/openAPI.yaml`) и генерируется на фронтенде через **`@hey-api/openapi-ts`** → SDK, типы, svelte-query hooks в `src/lib/api/generated/`, команда `npm run gen:api`.

Полный конвейер — в [`docs/contracts/rest-api.md`](./contracts/rest-api.md).

**Последствия.**

- При изменении API фронтенд регенерируется и все сгенерированные файлы коммитятся вместе с кодом.
- Сгенерированный код — источник истины для контрактов; страницы фронта никогда не вызывают `fetch` вручную (кроме XHR-загрузки файлов).
- Регенерация зависит от доступности удалённого URL спецификации — локальной редактируемой копии нет (см. [`debt.md`](./debt.md)).

## ADR-003: @tanstack/svelte-query + runes (без svelte/store)

**Контекст.** SPA активно читает и мутирует серверные данные; сущности вложены друг в друга (проповеди ↔ плейлисты ↔ разделы), поэтому нужна централизованная инвалидация кэша. Локальное состояние во Svelte 5 удобнее держать на runes, чем на классических writables `svelte/store`.

**Решение.** Серверное состояние — через **`@tanstack/svelte-query`**: `createQuery`/`createMutation` + сгенерированные hooks из `@tanstack/svelte-query.gen.ts`; инвалидация — через `invalidate*.ts` (`invalidateSermon`, `invalidatePlaylist`, `invalidateSection`), т.к. сущности встраивают друг друга. Локальное состояние — только **runes** (`$state`, `$derived`, `$effect`), без `svelte/store` writables. Оптимистичный reorder — через локальный `$state` + снапшот + `hasOrderChanged`.

**Последствия.**

- Правило: серверное состояние — только через svelte-query, локальное — только через runes.
- Каждая операция имеет `...Options` (для query) и `...Mutation`; после мутации вызывается инвалидация затронутых сущностей.
- `svelte/store` не используется; состояние не раскидывается по внешним сторам.

## ADR-004: formatReference нотация `глава:стих`

**Контекст.** Проповедь ссылается на библейскую книгу с главой и стихами (`book`, `chapter`, `verse`). Клиенты (сайт, admin, mobile) должны отображать ссылку единообразно в русской локали, с поддержкой диапазонов стихов и глав.

**Решение.** Утилита `formatReference` на фронте формирует русскую ссылку в нотации **`глава:стих`**, например `Иоанна 3:16` (одиночный стих), `Иоанна 3:16–18` (диапазон стихов) и `Иоанна 3:9–18, 20` (разрозненные отрезки стихов). Диапазон глав расширяет нотацию: `Иоанна 3:16–4:2` (диапазон стихов через границу глав) и `Иоанна 3–4` (только диапазон глав; пары «диапазон глав + одиночный стих» и «диапазон глав + отрезки» backend отклоняет, поэтому отображение деградирует до `3–4`, а не врёт). Входные данные парсятся `parseVerseInput`/`parseChapter` → `number | [start, end] | VerseSegment[] | null`; одиночный/диапазонный/отрезочный формат и `formatVerse`/`formatChapter` живут в `src/lib/utils/labels.ts` (`formatChapter` остаётся экспортированным как часть тулкита нотации). На проводе массив из двух целых чисел всегда читается как диапазон, поэтому форма оборачивает одиночные стихи в `[n, n]` при вводе «9, 20» — в отображении это невидимо (`9, 20`).

**Последствия.**

- Единая русская нотация `глава:стих` на всех экранах проповеди, включая диапазоны глав.
- `verse` и `chapter` хранятся как JSON (`number | number[]`) на бэкенде и генерируются в union-тип zod; `verse` дополнительно допускает массив отрезков (`[[9,18],20]`).
- Нотация фиксирована в документации модуля sermons ([`features/sermons.md`](./features/sermons.md)) — менять её — значит менять контракт отображения.

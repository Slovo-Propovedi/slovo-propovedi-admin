# Стек и решения (decisions)

Этот документ фиксирует **утверждённый стек** и принятые решения (ADRs). Изменения вносятся только через обсуждение и редактирование этого файла. Агенты НЕ добавляют зависимости вне секции Approved stack без объяснения «почему» в этом же документе. Каждое решение оформлено по схеме **Контекст / Решение / Последствия**.

## ADR-001: Разделение админки и API в отдельные репозитории

**Контекст.** Сейчас admin-панель — монорепозиторий с двумя приложениями (`backend/` NestJS API + `frontend/web-app/` Svelte SPA) и общей Docker-инфраструктурой. API потребляет несколько клиентов платформы (сайт, mobile), и его изменения по ритму и ответственности не совпадают с изменениями админ-интерфейса. Фронтенд развивается независимо и не обязан коммититься/версионироваться вместе с бэкендом.

**Решение.** Вынести админ-фронтенд в **отдельный git-репозиторий**, а этот репозиторий оставить чисто API-репозиторием (backend + инфраструктура + общий контракт). Контракт между ними — общий OpenAPI (уже живёт во внешнем swagger-репозитории `slovo-propovedi-docs`), поэтому git-расположение сторон не влияет на их связность.

**Последствия.**

- Документация уже разложена по репозиториям-целям: `docs/frontend/` переезжает с фронтендом, `docs/backend/` остаётся с API, `docs/contracts/` — общий для обоих.
- Каждое приложение получает собственный цикл CI, релизов и версионирования.
- До фактического разделения репозиторий остаётся монорепозиторием: оба приложения коммитятся вместе, а `Makefile` оркеструет их.
- Потребуется перенести инфраструктурные артефакты, общие для обоих приложений (в первую очередь `docker-compose.yml`), в подходящий репозиторий.

## ADR-002: OpenAPI-first кодогенерация

**Контекст.** У платформы несколько клиентов (сайт, admin, mobile), которые потребляют один REST API. Ручное дублирование типов и клиентов по сторонам неизбежно рассинхронизируется и порождает баги контрактов. Одна спецификация, сгенерированная в разные клиенты, — единая точка истины.

**Решение.** Единая OpenAPI-спецификация v0.4.0 «Admin API — Слово.Проповеди» — источник истины. Она живёт во **внешнем swagger-репозитории** (URL `https://docs.slovo-propovedi.ru/openAPI.yaml`) и генерируется с обеих сторон:

- **backend** → **Orval** → zod-схемы в `backend/src/generated/index.ts` (`strict` во всех контекстах), команда `npm run gen:schemas`;
- **frontend** → **@hey-api/openapi-ts** → SDK, типы, svelte-query hooks в `frontend/web-app/src/lib/api/generated/`, команда `npm run gen:api`.

Полный конвейер — в [`contracts/rest-api.md`](./contracts/rest-api.md).

**Последствия.**

- При изменении API регенерируются **обе** стороны в том же PR, и все сгенерированные файлы коммитятся вместе с кодом.
- Сгенерированный код — источник истины для контрактов; страницы фронта никогда не вызывают `fetch` вручную (кроме XHR-загрузки файлов).
- Регенерация зависит от доступности удалённого URL спецификации — локальной редактируемой копии нет (см. [`debt.md`](./debt.md)).

## ADR-003: nestjs-zod вместо class-validator (бэкенд)

**Контекст.** Бэкенд получает готовые zod-схемы из Orval (строгие, `strictObject`). `class-validator`/`class-transformer` не покрывают эти схемы напрямую и привели бы к дублированию валидации на двух моделях.

**Решение.** Валидация на бэкенде строится на **`nestjs-zod`**: глобальный `ZodValidationPipe` с `strictSchemaDeclaration: true` проверяет входные body/query/params, а `@ZodResponse()` + глобальный `ZodSerializerInterceptor` — исходящие ответы. DTO — классы вида `class CreateSermonDto extends createZodDto(SermonControllerCreateBody) {}`, при необходимости `.extend(...)` для уточнения (например, coercion `take`). `class-validator` остаётся только на сущности `User` (не используется для HTTP-валидации).

**Последствия.**

- Одна модель валидации (zod), совпадающая с контрактом из OpenAPI; строгая проверка отбрасывает лишние ключи на границе.
- Правило: каждый параметр маршрута обязан быть zod-DTO, иначе глобальный pipe бросает ошибку.
- `class-validator`/`class-transformer` остаются в зависимостях только ради `User`-сущности.

## ADR-004: @tanstack/svelte-query + runes (без svelte/store)

**Контекст.** SPA активно читает и мутирует серверные данные; сущности вложены друг в друга (проповеди ↔ плейлисты ↔ разделы), поэтому нужна централизованная инвалидация кэша. Локальное состояние во Svelte 5 удобнее держать на runes, чем на классических writables `svelte/store`.

**Решение.** Серверное состояние — через **`@tanstack/svelte-query`**: `createQuery`/`createMutation` + сгенерированные hooks из `@tanstack/svelte-query.gen.ts`; инвалидация — через `invalidate*.ts` (`invalidateSermon`, `invalidatePlaylist`, `invalidateSection`), т.к. сущности встраивают друг друга. Локальное состояние — только **runes** (`$state`, `$derived`, `$effect`), без `svelte/store` writables. Оптимистичный reorder — через локальный `$state` + снапшот + `hasOrderChanged`.

**Последствия.**

- Правило: серверное состояние — только через svelte-query, локальное — только через runes.
- Каждая операция имеет `...Options` (для query) и `...Mutation`; после мутации вызывается инвалидация затронутых сущностей.
- `svelte/store` не используется; состояние не раскидывается по внешним сторам.

## ADR-005: Ручные SQL-миграции (без TypeORM migrations)

**Контекст.** Схема PostgreSQL в проде живёт за **PgBouncer** (transaction mode), который запрещает DDL через пулер. TypeORM `synchronize: false`, а миграционный раннер TypeORM не используется — он бы требовал DDL через соединение и не сочетался с PgBouncer.

**Решение.** Схема и миграции — **ручной SQL**:

- `backend/sql/bootstrap.sql` — полная схема для свежей БД (совпадает с `synchronize`-выводом TypeORM);
- `backend/sql/migrate-add-username.sql`, `backend/sql/migrations/001_add_positions.sql` — идемпотентные одноразовые миграции;
- применяются вручную (`psql -f <file>`), без миграционного раннера.

Подробности — в [`backend/db.md`](./backend/db.md).

**Последствия.**

- Схему и миграции приходится поддерживать руками — это долг (см. [`debt.md`](./debt.md)).
- Настройки TypeORM адаптированы под PgBouncer: `synchronize: false`, `installExtensions: false`, `poolSize: 5`.
- Любое изменение схемы добавляется как отдельный идемпотентный SQL-файл.

## ADR-006: formatReference нотация `глава:стих`

**Контекст.** Проповедь ссылается на библейскую книгу с главой и стихами (`book`, `chapter`, `verse`). Клиенты (сайт, admin, mobile) должны отображать ссылку единообразно в русской локали, с поддержкой диапазона стихов.

**Решение.** Утилита `formatReference` на фронте формирует русскую ссылку в нотации **`глава:стих`**, например `Иоанна 3:16` (одиночный стих) и `Иоанна 3:16–18` (диапазон). Входные данные парсятся `parseVerse` → `number | [start, end] | null`; одиночный/диапазонный формат и `formatVerse` живут в `src/lib/utils/labels.ts`.

**Последствия.**

- Единая русская нотация `глава:стих` на всех экранах проповеди.
- `verse` хранится как JSON (`number | number[]`) на бэкенде и генерируется в union-тип zod.
- Нотация фиксирована в документации модуля sermons (`frontend/features/sermons.md`, `backend/modules/sermon.md`) — менять её — значит менять контракт отображения.
